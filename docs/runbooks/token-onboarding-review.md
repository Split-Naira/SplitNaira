# New Token Onboarding: Operational Review Checklist

**Owner:** Contract admin proposes and signs the allowlist transaction;
Backend on-call validates API and listener behavior; the release approver owns
the final go/no-go decision.

This checklist covers adding a Stellar token contract to SplitNaira's global
allowlist. The contract's `allow_token` entry point requires the configured
admin signature. The backend route `POST /splits/admin/allow-token` only builds
an unsigned XDR; it does not custody a key or add the token by itself.

## Before approval

- [ ] Record the canonical token contract address, network, issuer/owner,
  decimals, display name, symbol, and an independent source for each value.
- [ ] Confirm the address is a valid Stellar contract address and matches the
  intended network; never reuse a testnet address on mainnet.
- [ ] Verify the token contract implementation, transfer behavior, and any
  admin/freeze/clawback controls with the token issuer.
- [ ] Review the token's regulatory, sanctions, custody, liquidity, and
  support risks with the designated business/security owners.
- [ ] Confirm the current allowlist with
  `GET /splits/admin/allowlist?start=0&limit=<count>` and check that the token
  is not already present. Fetch the list in one read when practical because
  pagination can shift while the allowlist is changing.
- [ ] Confirm `PAYMENTS_ADMIN_API_KEY` access, and that
  `PAYMENTS_ADMIN_WRITE_ENABLED=true`; do not bypass the emergency write
  freeze for an onboarding.

## Staging rehearsal

- [ ] Build the XDR through `POST /splits/admin/allow-token` using the staging
  admin and token addresses, then have the admin signer inspect and sign it.
- [ ] Submit it on staging and verify
  `GET /splits/admin/is-token-allowed?token=<TOKEN>` returns `isAllowed: true`.
- [ ] Create a minimal test project using the token; exercise deposit and a
  distribution/claim path with non-production funds.
- [ ] Confirm the event listener catches up: `/ops/status` shows a healthy
  listener and `splitnaira_event_listener_ledger_lag` is not sustained above
  the warning threshold.
- [ ] Capture the staging transaction hash and request IDs in the change
  record.

## Production change

- [ ] Obtain the required approval and schedule a monitored change window.
- [ ] Re-verify the token address against the approved record immediately
  before signing; use a hardware/managed signer according to key policy.
- [ ] Submit the signed `allow_token` transaction and record its hash.
- [ ] Verify `is-token-allowed` and `allowlist` against the deployed mainnet
  contract, then run one small, approved end-to-end project flow.
- [ ] Monitor `/health/ready`, `/ops/mainnet-readiness`, listener ledger lag,
  RPC retry alerts, and failed transaction logs for at least 15 minutes.

## Rollback and impact

If the token must be removed before it is used, have the contract admin submit
the unsigned XDR generated by `POST /splits/admin/disallow-token`, then verify
the allowlist. **Do not disallow a token with active project balances or
in-flight payouts** without an incident review: existing project operations may
become unavailable. Preserve the request ID and transaction hash for audit and
follow [Stuck payouts](./stuck-payouts.md) if settlement is affected.

Adding a token changes the set of assets new projects can use. It does not
modify existing project token assignments, deploy new backend code, or require
a database migration.
